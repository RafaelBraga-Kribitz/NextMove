    fragments into one DuckDB statement that ASOF LEFT JOINs the canonical `events` table onto a
    `(customer_id, as_of_ts)` grid relation with the join predicate `grid.as_of_ts >= events.ts`.

    that event, and an event one microsecond later does not. State that boundary in the function's
    docstring so it is a decision rather than an accident of operator choice. End the statement with
    an explicit `ORDER BY grid.customer_id, grid.as_of_ts` so the returned row order is deterministic
    rather than dependent on execution plan.

    Declare `compute_as_of(customer_ids, as_of_ts, resolved, out_root=None) -> Table`, importing
    `Table` with `from nextmove.storage import Table`. Do **not** annotate against `pyarrow.Table`
    and do not add a `TYPE_CHECKING`-guarded `pyarrow` import: plan 01-04's second import contract
    lists `nextmove.features` among its source modules and forbids `pyarrow`, so a direct import
    drives `lint-imports` red and a bare unresolved annotation would leave a name that never resolves.
    `Table` is the public alias plan 01-06 re-exports from `nextmove.storage` for exactly this
    purpose — importing it is an import of the storage package, which every package is permitted, and
    it keeps the library named in exactly one place. The contract is not relaxed and no linter
    carve-out is added anywhere.

    The function builds a one-timestamp grid for the given customers and runs the composed SQL
    through the storage layer's `query`, passing `root=out_root`. Reject a naive `as_of_ts` with an

    Declare `COMPUTE_AS_OF_MAX_CUSTOMERS` as a module constant (use `10_000`) and raise a `ValueError`
    naming the limit, the supplied count and `materialize_grid` when `customer_ids` exceeds it.
    `query` returns a **fully materialized** Arrow table, so this function's memory cost is its result
    size; it is the on-demand path that Phase 2's decision endpoint calls for one customer or a
    handful, and it must not quietly become the bulk path. One timestamp times ten thousand customers
    is a small table; the whole population times the whole horizon is not, and the difference between
    them is a caller's argument. Making the boundary an explicit raise rather than a docstring
    warning is what keeps it from being crossed by accident.

    Declare `GRID_CHUNK_CUSTOMERS` as a module constant (use `5_000`) and
    `materialize_grid(resolved, out_root=None, chunk_customers: int = GRID_CHUNK_CUSTOMERS) -> Path`,
    which materializes the full daily grid — one row per active customer per day across the configured
    horizon per D-19 — **in customer-id-ordered chunks streamed straight to disk.**

    Obtain the active-customer id list once, through `query`, and slice it into chunks. That list is
    the **one** thing this function materializes as Python objects, and it is bounded by
    `n_customers` — 50 000 ids at default scale, the same population bound plan 01-08 accepts for
    `customer_traits`. Nothing else in this function may be converted out of Arrow; in particular no
    grid result may be, and the acceptance criteria pin that distinction by inspecting this function's
    AST rather than by grepping the file, precisely so the bounded call stays legal and the unbounded
    one stays forbidden.

    For each chunk of at most `chunk_customers` active customers, taken in ascending `customer_id`
    order: compose the identical ASOF SQL over that chunk's grid relation and hand it to the storage
    layer's `write_query_to_part(sql, part_dir="feature_grid", part_index=n,
    sort_key=("customer_id", "as_of_ts"), root=out_root, **table_bindings)`. That function streams
    DuckDB's result into a staging part file a row group at a time, so a chunk's rows are never all
    live at once and the grid as a whole is never one object. After the last chunk, call
    `list_part_files("feature_grid", root=out_root)` and merge with `write_table_from_parts` into
    `Zone.features`, sorted by `("customer_id", "as_of_ts")`, with `producer_stage=Stage.features`,
    the `ResolvedConfig` as `resolved_config`, `extra_metadata={"feature_set_version":
    FEATURE_SET_VERSION}`, and the resolved path of the canonical `events` table as its single entry
    in `input_paths`. Then call `clear_staging(root=out_root)` once. If the part list is empty — no
    active customers — call `write_table` with an empty row set instead, since plan 01-06 makes a
    zero-part merge raise for want of a schema.

    **Why this shape rather than the obvious one.** The earlier specification was "run the composed
    SQL and write `feature_grid` through `write_table`", and the two ends of that sentence do not
    compose: `query` returns an Arrow `Table` and `write_table` declares its first parameter as an
    iterable of Pydantic models or mappings. The only literal route between them is
    `write_table(grid.to_pylist(), …)`, which materializes the entire grid as Python dictionaries —
    the number of active customers times the configured horizon days, roughly 50 000 × 548 ≈ **27.4
    million rows** at the shipped default, on the one producer in this phase that carried no memory
    budget of any kind. Extending `write_table` to accept an Arrow table would fix the type mismatch
    and fix nothing else, because `query` would still have materialized the whole grid before handing
    it over; that is the relocate-the-peak move that this review cycle exists to stop. Streaming
    chunked query results into parts removes the materialization instead, and reuses the exact
    flush-and-merge pattern plans 01-08 and 01-09 already use, so the phase has one bounded write
    shape rather than three unrelated ones.

    Peak memory for this stage is therefore: DuckDB's working set for one chunk's ASOF join and sort,
    capped by plan 01-06's `STORAGE_MEMORY_LIMIT_MB` spill threshold, plus one Parquet row group. It
    does not grow with the population, because the population is chunked, and it does not grow with
    the horizon, because the result is streamed. `chunk_customers` is a parameter with a
    module-constant default and deliberately not a config key, for the same reason as plan 01-08's
    flush knobs: it changes how much is in flight, never which rows are produced or in what order, and
    the invariance is asserted by test.

    Pass paths, not hashes, to `input_paths`: the storage layer computes every content hash itself
    from the bytes on disk and derives the stamped input table names from the filename stems, which is
    what makes the lineage row unforgeable. And pass the `ResolvedConfig` object as `resolved_config`
    rather than the config hash string — that is what plan 01-06's declared parameter takes, and the
    storage layer derives the hash from it.

    `FEATURE_SET_VERSION` reaches the file through `extra_metadata`, which plan 01-06 declares for
    this purpose and which merges into, never overrides, the closed metadata set. Do not attempt to
    stamp it any other way: `write_table` and `write_table_from_parts` stamp a closed set of four keys
    and nothing else, so before that parameter existed there was no route for this constant into the
    table's metadata at all, and an executor would have silently dropped it — there was no criterion
    asserting it landed. There is one now.

    That sort key is a two-column tuple whose trailing column repeats — the grid holds one row per
    customer per day, so `as_of_ts` recurs once per customer — and it is legal because plan 01-06
    requires the key *tuple* to be unique across the rows rather than its final column.
    `(customer_id, as_of_ts)` is unique by construction here, which is what makes the order total and
    the bytes stable. It is also unique within every chunk, since a chunk is a set of whole customers,
    so each part file satisfies the precondition on its own as well as after the merge.

    Forward `out_root` to every storage call as `root` — to `query`, to `read_table`, to
    `table_exists`, to `write_query_to_part`, to `list_part_files`, to `write_table_from_parts`, to
    `write_table` and to `clear_staging`. Both functions accept the parameter and neither may drop it:
    plan 01-11 runs the whole pipeline twice into two separate output roots and compares every
    produced file's sha256, and a features stage that ignored its root would write both runs' grids
    to the same path and make that comparison vacuous.

    `feature_grid` is the only table this stage writes, and `data/features/` is the only directory it

    dependency, so a write into it — which is what would happen if lineage still lived there — would
