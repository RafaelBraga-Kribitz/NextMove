<objective>
Close UAT gap G-01-1: the default-profile pipeline is unrunnable because `write_table_from_parts()`
stacks a `QUALIFY row_number() OVER (...)` window operator and an outer `ORDER BY` into one DuckDB
query. When `dedupe_on` differs from `sort_key` — the ingest events merge, and only that call site —
DuckDB must run two independent full-dataset external sorts in one query plan, which is a documented
DuckDB memory-accounting hazard: the combined working set is not bounded by `memory_limit` even
though each operator alone spills fine. At 24.7M rows under the intentional
`STORAGE_MEMORY_LIMIT_MB = 512` ceiling this aborts ingest at ~79% with
`OSError: Out of Memory Error: failed to pin block of size 256.0 KiB (488.0 MiB/488.2 MiB used)`.
Confirmed synthetically at 3M and 6M rows with the byte-identical error signature
(.planning/debug/ingest-oom-default-scale.md).

Purpose: phase success criterion 1 ("regenerates the full simulated history ... byte-identical across
two seeded runs") and ENG-08's laptop guarantee are both unprovable while the ingest stage cannot
finish at the profile the committed `dvc.yaml` targets.

Output: a two-stage merge (materialize the deduped result, then sort it in a separate query on a
separate connection), a corrected docstring, and three tests — one that fails on the current
implementation and passes on the fixed one, one control proving the old shape really does exhaust the
same budget, and one runtime guard that no single executed statement ever dedupes and sorts again.
</objective>

  `part_dir` that escapes the staging root.
- `clear_staging(part_dir=None, root=None)` — removes one staging subdirectory; refuses anything not
  under the staging root.
- `list_part_files(part_dir, root=None)` — globs `part-*.parquet` inside one staging subdirectory
  only, so a differently named subdirectory is invisible to it.

    When `dedupe_cols` is None: keep today's behaviour unchanged — one connection, one
    `SELECT * FROM read_parquet([...]) ORDER BY <order_by>` statement, `to_arrow_reader` into

    DuckDB's own remediation for stacked blocking operators ("break it into stages and materialize"):

    Stage 1 (dedupe, materialize). Resolve an intermediate path with
    `resolve_staging_path(part_dir=f"_merge_dedupe_{table_name}", part_index=0, root=root)`. The
    leading underscore and the `_merge_dedupe_` prefix keep it outside every real part directory, so
    `list_part_files` can never pick it up as an input part. Unlink any pre-existing file at that path
    first so a crashed earlier run cannot leak stale rows in. Open a connection, execute a single
    `COPY ( SELECT * FROM read_parquet([...]) QUALIFY row_number() OVER (PARTITION BY <dedupe cols>
    ORDER BY <order_by>) = 1 ) TO '<intermediate path>' (FORMAT PARQUET)` statement — note there is no
    outer `ORDER BY` in this statement, that is the entire point — then close the connection. Closing
    it releases the window operator's buffers and removes its spill files before the sort begins.

    Stage 2 (sort, stream out). Open a fresh connection, execute
    `SELECT * FROM read_parquet('<intermediate path>') ORDER BY <order_by>`, take
    `to_arrow_reader(PARQUET_ROW_GROUP_SIZE)` and hand it to `write_parquet_stream(reader, dest,
    sort_key, metadata)` exactly as today, then close the connection.

    Wrap both stages so that the intermediate is always removed — a `try/finally` whose `finally` calls
    `clear_staging(f"_merge_dedupe_{table_name}", root=root)`. The merge cleans up after itself rather
    than relying on the producer's later `clear_staging()`, because two of the three call sites are
    tests that never call it. Each connection gets its own `try/finally: con.close()` so a failure in
    stage 1 cannot leak a connection into stage 2.

    Keep using the existing `_sql_quote` and `_order_by_clause` helpers for every literal and every
    column list; do not hand-build quoting. Re-use `part_list_sql` as built today.

    is the memory limit plus one row group **at any table size**" is false as written and is what let
    this defect ship: it holds for the single-`ORDER BY` shape, and it did not hold for the chained
    window-plus-sort shape. Rewrite it to say, concretely: with no `dedupe_on` the merge is one
    blocking sort and the bound holds; with `dedupe_on` the merge is deliberately two separate queries
    on two separate connections, because stacking a window operator and an outer sort in one statement
    is a documented DuckDB memory-accounting hazard whose combined working set is not bounded by
    `memory_limit` — it aborted the 24.7M-row ingest events merge at 512MB (UAT gap G-01-1,
    .planning/debug/ingest-oom-default-scale.md) and reproduces synthetically. Name the intermediate's
    location and the fact that it is removed in a `finally`. Keep the existing paragraph warning
    against a whole-table Arrow concatenation and the existing `ValueError` paragraph.
