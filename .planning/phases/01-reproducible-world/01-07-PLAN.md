<objective>
Build the simulated world's static structure and its deterministic randomness substrate: per-entity
RNG streams, the virtual clock, latent-trait sampling, the seasonal catalog with its
low-seasonality contrast category, inventory and campaigns — all driven by
`config/simulator.yaml`.

Purpose: D-03 makes ground-truth uplift computable per (customer, action) pair, which is what lets
Phase 4 measure how wrong the propensity-as-uplift approximation is — a headline result the charter
wants. That is only possible if a customer's latent traits are stable and reproducible, which is a
property of how randomness is derived, not of the simulation logic layered on top.
Output: `World.initialize(config)` returning a fully-populated, deterministic world in memory.
</objective>

  <action>
    Create `src/nextmove/simulator/rng.py`.

    Declare `SeedDomain` as a StrEnum with members `world`, `organic`, `response`, `campaign`,
    matching the four fields of `SeedsConfig`. Declare
    `entity_rng(domain: SeedDomain, entity_id: int, seeds: SeedsConfig) -> np.random.Generator`
    returning `np.random.default_rng([entity_id, getattr(seeds, domain.value), domain_ordinal])`,
    where `domain_ordinal` is a stable integer index of the domain member. Passing a list of
    integers as entropy is what gives every entity an independent, reproducible stream that is
    immune to iteration order and to the population changing around it. Declare
    `stream_rng(domain, entity_id, tick, seeds)` for per-tick substreams, folding the tick index
    into the same entropy list.

    Draw exclusively through generators returned by these two functions. Do not call NumPy's
    legacy module-level seeding function or its module-level draw helpers anywhere in
    `src/nextmove/simulator/`: those share one global state, so the value a customer receives would
    depend on how many draws happened before them, which silently changes when the population grows,
    when iteration order changes, or when a loop is parallelized. Do not use the Python standard
    library `random` module either — it has the same global-state problem and a different stream.

    Add a module docstring stating that any sequence derived from a `set` or from `dict` key order
    must be explicitly sorted before it influences a draw, because Python randomizes string hashing
    per process.

    Create `src/nextmove/simulator/clock.py` declaring `SimClock` with `start_date: date` and
    `horizon_days: int`, and methods `timestamp_for_tick(tick) -> datetime` (midnight UTC of
    `start_date + tick days`, raising `IndexError` naming the tick when it falls outside the
    half-open range 0 to `horizon_days`), `intraday(tick, seconds_offset) -> datetime`, and
    `ticks() -> Iterator[tuple[int, datetime]]`. Every returned datetime is timezone-aware UTC.
    Never read the host clock: the simulation's time axis is the config start date plus the tick
    index, and a wall-clock reading would make two runs differ and would break both DATA-03's
    monotonicity gate and the ASOF joins in plan 01-10.

    Create `tests/unit/test_rng_determinism.py` covering every item in the behavior block. Include
    the order-independence test as a direct comparison: build the traits-relevant draws for a fixed
    customer id three times — visiting ids ascending, descending, and shuffled with a seeded
    shuffler — and assert all three sequences are equal.
  </action>
