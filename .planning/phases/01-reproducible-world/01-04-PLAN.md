<objective>
Make SIM-02 real: an import-linter forbidden contract that fails CI when any module under
`models/`, `decisions/`, `policies/` or `features/` imports `nextmove.simulator`, plus a second
contract that keeps Parquet and DuckDB access confined to `nextmove.storage` (ENG-01's thin
repository layer). Wire both into a Linux-only GitHub Actions workflow (D-16).

Purpose: CONTEXT.md calls this "the single most load-bearing test in the phase — if simulator
internals reach the models, every downstream result is fake." RESEARCH Pitfall 4 documents the way
this fails silently: the contract exists, exits 0, and checks nothing. This plan therefore ships the
contract *and* a machine proof that the contract has teeth.
Output: phase success criterion 4 becomes mechanically true.
</objective>

<planner_notes>
**Static type checking is deferred to Phase 2 — a decision, not an oversight (review LOW-2).**
Cross-AI review cycle 1 observed that no plan in this phase mentions `mypy` or `pyright`, and that
the omission was silent rather than reasoned. It is now reasoned, and Task 3 writes the reasoning
into `.github/workflows/ci.yml` so it reaches every future reader of the workflow rather than living
only in a planning document.

The decision is to **defer**, for three reasons. First, ENG-02 — the eight typed plugin registries
that are the main thing a type checker would protect — is Phase 2 scope; adding the checker before
the typed surface it guards exists buys little and costs a full annotation pass over code that is
about to be extended. Second, D-16 forbids any CI step that can swallow a failure, and T-01-09
enforces that with `continue-on-error` and `|| true` both asserted absent; a type checker introduced
mid-phase would therefore be a hard gate from its first commit, and on a greenfield tree with
`pyarrow`, `duckdb` and `pandera` stub gaps it would go red for reasons unrelated to this phase's
goals. Third, the safety this phase actually depends on is enforced at runtime and by test —
Pydantic validates every contract with `extra="forbid"`, and the import boundary is checked by
`import-linter` — so the residual risk of deferring is narrower than it first appears.

Accepted cost, stated plainly: Phase 1 ships without a static type gate, so a type error that
neither Pydantic nor a test exercises can reach `main`. The obligation to close it belongs to Phase 2
alongside ENG-02, and this plan's SUMMARY carries it forward so phase verification sees it.

**Annotation-only references to forbidden libraries: decided, and contract two is not relaxed
(review cycle 2, MEDIUM-6).** Cycle 2 found that plan 01-10 declared an Arrow return annotation
inside `nextmove.features`, which contract two below lists as a source module and forbids from
importing `pyarrow`. The flagged SIM-02 assumption in this plan's frontmatter already named
"a TYPE_CHECKING-guarded import" as an open edge, so the category was known but undecided. It is
decided now.

**No carve-out is added to either contract, and `include_external_packages` stays on.** Both of the
obvious relaxations were rejected: excluding `nextmove.features` from contract two's source list
would remove the very package most likely to reach for DuckDB, and configuring the linter to ignore
`TYPE_CHECKING` blocks would make the contract blind to a whole class of import that is still a real
coupling in the source text.

Instead the dependency is inverted: `nextmove.storage` re-exports a public `Table` alias for the
Arrow table type (plan 01-06), and every consumer annotates against `from nextmove.storage import
Table`. That is an import of a first-party package which no contract forbids, it resolves at runtime
so the annotation is real rather than dangling, and it keeps `pyarrow` named in exactly one package
— which is the same property ENG-01's thin repository layer exists to produce. A future contributor
who needs an Arrow type in a consumer package has one sanctioned route and no reason to reach for a
guarded import. If a genuinely un-aliasable annotation ever appears, that is a new decision to make
in review, not a linter setting to loosen quietly.
</planner_notes>
