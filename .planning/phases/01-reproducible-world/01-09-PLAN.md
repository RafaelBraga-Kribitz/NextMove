<planner_notes>
**Resolved RESEARCH open question 3.** RESEARCH asked whether Pandera is needed or whether Pydantic
validators alone suffice for DATA-03, and recommended including Pandera for the whole-dataframe
checks (monotonic timestamps within a session, referential integrity to the catalog) that are awkward
as single-row validators. This plan adopts the recommendation: Pydantic owns per-row contract
validation, Pandera owns the cross-row semantic gates, and the two produce reject rows in the same
shape.

**Scale of double validation (cross-AI review cycle 1, the reviewer's Pandera/Pydantic LOW; cycle 2,
HIGH-9).** The reviewer noted that per-row Pydantic validation followed by a whole-dataframe Pandera
sweep is robust but potentially slow and memory-hungry over the full 50k-customer history. The
orchestrator recorded it as the same root cause as MEDIUM-1.

Cycle 1's amendment claimed to close it by batching, and cycle 2 found that the claim and the
mechanism disagreed: the batch loop bounded the *validation* frontier, but the landing step then
read the existing table, unioned it with the new events, deduplicated and globally sorted before a
single terminal `write_table` — which requires every valid `Event` from every batch to be live at
once, plus the whole pre-existing canonical table. Peak memory was still the full event set, the
`write_table_from_parts` named in `read_first` was never called, and the streaming acceptance
criterion could not pass, because under a single terminal write the input generator is necessarily
exhausted before the first write.

It is closed properly here by mirroring plan 01-08 Task 3 rather than describing it:

1. **Each validated batch leaves Python.** After validation, a batch is written to a staging part
   file through `write_part_file` and the batch's `Event` objects are released. Nothing accumulates
   across batches. The first part file therefore lands after the *first* batch, which is what makes
   the streaming criterion satisfiable rather than self-contradictory.
2. **The union, dedupe and sort move into the storage layer.** `write_table_from_parts` takes the
   part paths plus, when it exists, the pre-existing canonical table as an additional input part,
   applies `dedupe_on="event_id"`, sorts by `CANONICAL_SORT_KEY` and writes once. The reduction
   happens in Arrow inside plan 01-06's single write site, so idempotent append no longer costs a
   Python-side union, and the merged bytes remain identical to a single unbatched write.
3. **The path gets a budget.** `tests/integration/test_ingest_budget.py` states a peak-heap number
   and asserts it, because the reason this defect survived a cycle is that nothing in the suite
   measured this path — `test_simulation_budget.py` is simulator-only.

Neither validation is dropped or sampled — DATA-02 and DATA-03 both require every row to be checked,
and a sampled gate would be a gate in name only. What changes is the working-set size, not the
coverage.

**Re-ingest semantics under `dvc repro` (cycle 2, MEDIUM-5).** The append-only union above is real,
but it is reachable only on the direct invocation path. Plan 01-11 declares `data/canonical/` as the
`ingest` stage's `outs` with no `persist` flag, and `dvc repro` removes a stage's non-persistent outs
before executing it — so under the pipeline the "read the existing table if present" branch never
finds one and every pipeline run is a full rebuild from `data/raw/`. That is stated explicitly in
Task 1 rather than left for a reader to infer, and plan 01-11 adds the acceptance criterion that
actually tests it, by forcing a re-execution and asserting the canonical digest is unchanged. The
two semantics are safe to hold simultaneously precisely because they are byte-equal for identical
input; if they ever diverge, that criterion goes red.
</planner_notes>
