<planner_notes>
**Resolved RESEARCH open question 3.** RESEARCH asked whether Pandera is needed or whether Pydantic
validators alone suffice for DATA-03, and recommended including Pandera for the whole-dataframe
checks (monotonic timestamps within a session, referential integrity to the catalog) that are awkward
as single-row validators. This plan adopts the recommendation: Pydantic owns per-row contract
validation, Pandera owns the cross-row semantic gates, and the two produce reject rows in the same
shape.

**Scale of double validation (cross-AI review cycle 1, the reviewer's Pandera/Pydantic LOW; cycle 2,
HIGH-9).** The reviewer noted that per-row Pydantic validation followed by a whole-dataframe Pandera
sweep is robust but potentially slow and memory-hungry over the full 50k-customer history. The
orchestrator recorded it as the same root cause as MEDIUM-1.

Cycle 1's amendment claimed to close it by batching, and cycle 2 found that the claim and the
mechanism disagreed: the batch loop bounded the *validation* frontier, but the landing step then
read the existing table, unioned it with the new events, deduplicated and globally sorted before a
single terminal `write_table` — which requires every valid `Event` from every batch to be live at
once, plus the whole pre-existing canonical table. Peak memory was still the full event set, the
`write_table_from_parts` named in `read_first` was never called, and the streaming acceptance
criterion could not pass, because under a single terminal write the input generator is necessarily
exhausted before the first write.

It is closed properly here by mirroring plan 01-08 Task 3 rather than describing it:

1. **Each validated batch leaves Python.** After validation, a batch is written to a staging part
   file through `write_part_file` and the batch's `Event` objects are released. Nothing accumulates
   across batches. The first part file therefore lands after the *first* batch, which is what makes
   the streaming criterion satisfiable rather than self-contradictory.
2. **The union, dedupe and sort move into the storage layer.** `write_table_from_parts` takes the
   part paths plus, when it exists, the pre-existing canonical table as an additional input part,
   applies `dedupe_on="event_id"`, sorts by `CANONICAL_SORT_KEY` and writes once. The reduction
   happens in Arrow inside plan 01-06's single write site, so idempotent append no longer costs a
   Python-side union, and the merged bytes remain identical to a single unbatched write.
3. **The path gets a budget.** `tests/integration/test_ingest_budget.py` states a peak-heap number
   and asserts it, because the reason this defect survived a cycle is that nothing in the suite
   measured this path — `test_simulation_budget.py` is simulator-only.

Neither validation is dropped or sampled — DATA-02 and DATA-03 both require every row to be checked,
and a sampled gate would be a gate in name only. What changes is the working-set size, not the
coverage.

**The half that three cycles of batching never touched (cycle 3, HIGH-11 and HIGH-12).** The concern
quoted above has two clauses, and every amendment so far addressed only the first. The second —
"followed by a whole-dataframe Pandera sweep" — survived intact: `run_semantic_gates` took a frame of
*all* landed events, ran outside `ingest_events`, and was therefore outside the only thing the budget
test measured. So the plan's own budget test structurally could not observe the largest allocation on
the ingest path.

Running the gates after `ingest_events` returned had a second, worse consequence than memory, which
cycle 3 filed separately as HIGH-12. `evaluate_reject_rate` reads `IngestResult.reject_rate`, and
that result is built and returned before any gate runs — so **D-21's threshold could never fire on a
semantic violation**, which is precisely the slow-degradation class DATA-03 exists to catch.
Semantically invalid rows also stayed in `events` (they were detected only after the merge landed the
table, and nothing removed them), making "quarantine" nominal; `gates_passed` and `gates_failed` were
declared but unpopulated because the function that builds the result never ran a gate; and the CLI
was told to write additional reject rows into "the same rejects table" after `clear_staging` had
already removed the staging tree, with no storage call specified for doing so.

Both are closed by one re-sequencing, which is why they are treated together: **the gates move inside
`ingest_events` and run per batch, before the flush.** A violating row is diverted into the rejects
part rather than the events part, so it never enters the canonical table; it is counted in the single
`IngestResult` that `evaluate_reject_rate` then reads, so the threshold covers both stages; the
result is built by the function that ran the gates, so `gates_passed` and `gates_failed` populate
from one place; and there is no post-hoc rejects write to specify because there is no post-hoc
rejection. The CLI shrinks to: run `ingest_events`, evaluate the rate, print the summary, set the
exit code.

Making the gates per-batch is a real design constraint rather than a relabelling, and each of the
three is handled explicitly in Task 2: the price gate is already per-row; the referential-integrity
gate becomes a membership test against a set built once from the catalog before the loop; and the
monotonicity gate — the only genuinely cross-row one — carries a bounded `session_id → last_ts` map
whose size tracks *concurrent* sessions rather than history, with an eviction rule and a stated
failure mode for a session that reappears after eviction. `must_haves` truth about every row being
validated by both the contract and the gates is preserved exactly: the batch size changes the working
set, never the verdict.

**And the merge's own footprint (cycle 3, HIGH-10).** Cycle 2's fix moved the union into
`write_table_from_parts`, which then concatenated every part into one Arrow table — so the
materialization was relocated out of the `tracemalloc` measurement rather than removed. Plan 01-06
now merges out of core through DuckDB under an explicit spill limit, and this plan's budget suite
asserts peak **process RSS**, which is the only instrument that can observe that half at all.

**Re-ingest semantics under `dvc repro` (cycle 2, MEDIUM-5).** The append-only union above is real,
but it is reachable only on the direct invocation path. Plan 01-11 declares `data/canonical/` as the
`ingest` stage's `outs` with no `persist` flag, and `dvc repro` removes a stage's non-persistent outs
before executing it — so under the pipeline the "read the existing table if present" branch never
finds one and every pipeline run is a full rebuild from `data/raw/`. That is stated explicitly in
Task 1 rather than left for a reader to infer, and plan 01-11 adds the acceptance criterion that
actually tests it, by forcing a re-execution and asserting the canonical digest is unchanged. The
two semantics are safe to hold simultaneously precisely because they are byte-equal for identical
input; if they ever diverge, that criterion goes red.
</planner_notes>

    Create `src/nextmove/ingest/pipeline.py`.

    Declare `PipelineStage` as a StrEnum with members `contract`, `semantic` and `lineage`, so a
    reject row states which gate produced it. Declare `RejectRecord` as a frozen Pydantic model with
    fields `reject_id`, `raw_record: str` (the original record serialized as canonical JSON so it
    survives verbatim and is inspectable), `reason: str`, `field_path: str | None`,
    `contract_version: str`, `stage: PipelineStage`, and `source: str`. Derive `reject_id`
    deterministically from the raw record's canonical JSON, the reason and the stage, using the same
    `uuid5` approach `derive_event_id` uses, so two runs produce identical reject ids.

    Declare `IngestResult` as a frozen model with `rows_in`, `rows_landed`, `rows_quarantined`,
    `rows_rejected_contract`, `rows_rejected_semantic`, `reject_rate`, `gates_passed: list[str]`,
    `gates_failed: list[str]`, `canonical_path` and `rejects_path`. The two per-stage counters exist
    because `RejectRateExceeded` is specified to carry per-stage reject counts and previously had no
    field to source them from, and because a reviewer reading the summary line needs to know whether
    a rate came from malformed payloads or from semantic violations — those have different causes and
    different fixes. `rows_quarantined` is their sum and `reject_rate` is that sum over `rows_in`.

    Declare `ingest_events(raw_records, resolved, adapter_name="simulator", out_root=None,
    batch_size: int = VALIDATION_BATCH_SIZE) -> IngestResult`, with `VALIDATION_BATCH_SIZE` a
    module-level constant (use `50_000`). Like plan 01-08's flush knobs it is a working-set control
    only: it must not change which rows land, which are rejected, or the resulting bytes, and it is
    deliberately a parameter with a module-constant default rather than a config key for exactly that
    reason. Resolve the adapter through `get_adapter`, then consume `raw_records` as
    an iterator in batches of `batch_size`, never as a materialized sequence — do not call `list()`,
    `tuple()` or `len()` on it, since any of those exhausts the input before the first write and is
    exactly the shape the streaming test below is written to catch.

    Forward `out_root` to every storage call as the `root` argument — to `read_table`,

    and `clear_staging`. Plan 01-06 gives all of them a `root` parameter for this reason, and an
    `out_root` this function accepts and then drops would leave the CLI's `--out` flag decorative
    and plan 01-11's two-output-root golden comparison unwritable.

    **Before the batch loop, build the gate state once.** Read the `catalog` table from `Zone.raw`

    the sku membership set the referential-integrity gate tests against. Construct one
    `SessionMonotonicityTracker` (Task 2). Both are hoisted out of the loop deliberately: the catalog
    is bounded by `n_skus` and the tracker by concurrent sessions, so both are bounded by
    configuration rather than by input length, and rebuilding either per batch would be the same
    whole-history sweep in a slower disguise.

    **Within each batch, validate, then gate, then flush.** Validate each record individually so one
    bad row never aborts the batch: on success collect the `Event`, on `ValidationError` build a
    `RejectRecord` whose `reason` is the flattened Pydantic error message, whose `field_path` is the
    error's location path and whose `stage` is `contract`. Never call a coercing constructor and never
    fall back to a permissive parse — DATA-02's requirement is that violations are quarantined, not
    repaired, because a repaired row is a fabricated observation.

    Then pass the batch's surviving `Event` objects through
    `run_semantic_gates(events_batch, catalog_index, tracker, config)` (Task 2). Partition the batch
    on the result: every event named by a gate violation is removed from the events list and becomes a
    `RejectRecord` with `stage=semantic` and a reason naming the gate and the failed check; the rest
    continue to the events part. **This ordering is the whole point of the amendment.** Running the
    gates here rather than over the landed table is what keeps semantically invalid rows out of
    `events` at all — the earlier design detected them only after the merge had already written the
    canonical table, so a row appeared in `events` *and* in `rejects` and quarantine was nominal — and
    it is what puts semantic rejections inside the single `IngestResult` that `evaluate_reject_rate`
    later reads, without which D-21's threshold could never fire on a semantic violation.

    Accumulate, across batches, only counters and gate outcomes — never rows: a running
    `rows_rejected_contract`, a running `rows_rejected_semantic`, and a per-gate violation count keyed

    `gates_passed` is the sorted list of configured gate names not in `gates_failed`. Populate both on
    the `IngestResult` this function returns. They were previously declared and never populated,
    because the only function that constructs an `IngestResult` never ran a gate — a small symptom of
    the same ordering defect, now closed by construction rather than by a separate assignment.

    Honour a gate marked fail-fast in config by raising immediately, naming the gate and the first
    violating row, rather than continuing to the flush. Every other gate quarantines and continues,
