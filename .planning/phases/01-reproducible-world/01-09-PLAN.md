<objective>
Land the canonical event store with a real quality gate: Pydantic contract validation with
quarantine (DATA-02 / D-20), Pandera semantic gates for negative price, session timestamp
monotonicity and catalog referential integrity (DATA-03), a configurable reject-rate threshold that
fails the run (D-21), and the one-line data-quality summary every run prints (D-22).

Purpose: phase success criterion 2's second half — malformed or semantically invalid events land in
a quarantine table with a stated reason or fail the run, and never enter the store silently.
Output: `data/canonical/` holding `events`, `rejects`, and the lineage rows that describe them.
</objective>

<planner_notes>
**Resolved RESEARCH open question 3.** RESEARCH asked whether Pandera is needed or whether Pydantic
validators alone suffice for DATA-03, and recommended including Pandera for the whole-dataframe
checks (monotonic timestamps within a session, referential integrity to the catalog) that are awkward
as single-row validators. This plan adopts the recommendation: Pydantic owns per-row contract
validation, Pandera owns the cross-row semantic gates, and the two produce reject rows in the same
shape.

**Scale of double validation (cross-AI review cycle 1, the reviewer's Pandera/Pydantic LOW).** The
reviewer noted that per-row Pydantic validation followed by a whole-dataframe Pandera sweep is
robust but potentially slow and memory-hungry over the full 50k-customer history. The orchestrator
recorded it as the same root cause as MEDIUM-1, and it is closed here the same way: `ingest_events`
consumes its input in batches and never materializes the whole event history as live Pydantic
objects, and the semantic gates run per batch for the row-local checks with only the cross-row
checks needing a wider view. Neither validation is dropped or sampled — DATA-02 and DATA-03 both
require every row to be checked, and a sampled gate would be a gate in name only. What changes is
the working-set size, not the coverage.
</planner_notes>

    Declare `GateResult` as a frozen model with `gate_name`, `passed: bool`, `violation_count`, and

    Implement three Pandera schemas, each registered in a module-level `SEMANTIC_GATES` mapping from
    gate name to a callable taking the candidate events dataframe plus the catalog and returning a
    `GateResult`. Run every schema with `lazy=True` so all violations are collected in one pass and
    each failure case carries its row index and check name — that structure maps directly onto the
    reject row's `reason` and `field_path` with no extra bookkeeping.

    `non_negative_price` — assert every monetary column across every payload type is greater than or
    equal to zero. Zero is legal (a free gift line, a fully-discounted item); minus one cent is not.
    State that boundary in the check's description so the intent is not re-litigated later.

    `monotonic_session_timestamps` — group by `session_id` and assert timestamps are strictly
    increasing within each group. Two events sharing a session and a timestamp are a violation, not a
    tie: within one session the ordering is causal, and equal timestamps mean the generator lost
    the causal order. Note that this differs deliberately from the canonical *table* sort, where
    equal timestamps across the customer's whole history are legitimate and broken by `event_id`.
    A single-event session trivially passes. Compare timestamps as timezone-aware UTC values only;
    RESEARCH Pitfall 1 documents that a naive value here either raises or silently misorders.

    `catalog_referential_integrity` — assert every sku referenced by any payload exists in the
    catalog table loaded from `Zone.raw`. Build the membership set from a sorted catalog column so
    the check's own iteration cannot influence output ordering.
