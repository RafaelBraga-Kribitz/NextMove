<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PyPI → local environment | Third-party package code is executed at install and import time; this is the only untrusted-input boundary in this plan |
| Developer shell → repository | `just`/`make` recipes execute arbitrary shell on the developer's machine |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-SC | Tampering | `uv add` / `uv sync` dependency installs (pypi) | high | mitigate | Task 1 is a `checkpoint:human-verify` with `gate="blocking-human"` executed BEFORE the first install; it confirms `dvc` resolves to `iterative/dvc` (the seam returned the wrong org) and spot-checks the other nine. `uv.lock` is committed and hash-pins every resolved distribution, so subsequent syncs cannot silently substitute a different artifact. Not auto-approvable regardless of `workflow.auto_advance`. |
| T-01-01 | Elevation of Privilege | `justfile` / `Makefile` recipes | low | accept | Recipes contain only literal commands with no interpolation of external input; `just` variables are limited to a `profile` string consumed by `--profile`. Accepted: a developer running recipes from their own repo already has shell access. |
| T-01-02 | Tampering | `.gitignore` omission leading to generated data being committed | low | mitigate | `data/`, `mlruns/`, and `mlflow.db` are ignored from the first commit so no generated artifact ever enters git history; DVC (plan 01-06) is the only tracker for `data/`. |
</threat_model>
