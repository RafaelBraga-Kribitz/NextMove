<objective>
Build the thin repository layer ENG-01 requires and the content-hash lineage DATA-04 requires, and
initialize DVC as the artifact-versioning mechanism ADR 007 ratified (ENG-09 / D-09).

Purpose: this is the single place where determinism is either won or lost. RESEARCH names four
documented nondeterminism sources — unsorted row order, multi-threaded DuckDB float aggregation,
hash-randomized set iteration, and wall-clock metadata in the Parquet footer — and every one of them
is a storage-layer concern. Fixing them once here means every later producer inherits the guarantee
instead of re-earning it.
Output: `write_table` / `read_table` / `query`, a queryable lineage table, a printable lineage chain,
and a golden test proving byte-identical writes before any simulator exists to test with.
</objective>

<planner_notes>
**Resolved RESEARCH open question 2.** RESEARCH asked whether lineage should live in Parquet
file-level key-value metadata or in a queryable sidecar table, and recommended the table. This plan
adopts the recommendation: the lineage table is the source of truth that `print_lineage_chain` reads
from, because CONTEXT.md uses "queryable" language for the sibling rejects table (D-20) and a
`SELECT` is far simpler to demonstrate than parsing a Parquet footer. A redundant copy is
additionally stamped into Parquet key-value metadata for portability, but nothing reads from it.

**Resolved cross-AI review finding cluster (HIGH-1 through HIGH-4).** Review cycle 1 found four
defects that all trace to one knot: this plan originally had `write_table` record lineage on every
write, while the lineage table itself lived in the `canonical` zone and was persisted *through*
`write_table`. That single loop produced unbounded re-entry (HIGH-1), a two-way module import
(HIGH-2), a DVC stage-output overlap because every stage then wrote into `ingest`'s output directory
(HIGH-3), and a self-contradictory anti-forgery contract because the caller had to supply the hash
(HIGH-4). The knot is cut once, with three structural consequences that are separately checkable:

1. **A private write primitive underneath both public modules.** `_parquet.py` owns the sorted
   atomic Parquet write and the raw read. `repository.py` and `lineage.py` both build on it, and
   `lineage.py` imports neither `repository.py` nor anything that imports it. The storage import
   graph becomes a DAG, so no lazy-import workaround is needed. *(Closes HIGH-2 — an `ImportError`
   at package load.)*
2. **Lineage is persisted by the private primitive, never by `write_table`, and `write_table`
   refuses the lineage zone.** Recording lineage therefore cannot re-enter the recording path at
   all, and the refusal makes the intent explicit rather than emergent. `write_table` additionally
   carries an explicit `record_lineage: bool = True` switch for callers that must write without
   recording. *(Closes HIGH-1 — a `RecursionError` at run time. Distinct failure mode from HIGH-2,
   distinct mechanism, distinct acceptance criteria.)*
3. **Lineage gets its own zone and one fragment file per producing stage.** `data/lineage/` holds
   `simulate.parquet`, `ingest.parquet` and `features.parquet`. Each pipeline stage writes only its
   own fragment and reads none of the others, so no stage writes into a directory another stage
   owns and each fragment is declarable as an `out` of exactly one DVC stage. `data/canonical/`
   holds only `events` and `rejects`. *(Closes HIGH-3, and with it the unsatisfiable `dvc.lock`
   idempotency criteria in plan 01-11.)*

**Anti-forgery contract made achievable (HIGH-4).** The original plan simultaneously required
`write_table` to pass the hash in and forbade `record_lineage` from accepting one. The contract is
now: the caller supplies the destination `Path` and a `LineageRecordDraft` that has **no hash field
of any kind** except `config_hash`; `record_lineage` computes the described table's `content_hash`
and every input's hash itself, from the bytes on disk, and returns the completed `LineageRecord`.
The property that is actually enforceable — a producer cannot assert a hash it did not earn — is
what the acceptance criteria now check, including a test that mutates the file after the draft is
built and asserts the recorded hash tracks the file rather than the caller. `config_hash` remains
caller-supplied because it is a property of the configuration, not of any file; that residual is
recorded in T-01-14.

**Resolved cross-AI review cycle 2 (HIGH-5, HIGH-6, HIGH-8, MEDIUM-6).** Review cycle 2 found that
three of the four producers describe calls this API cannot service, and that one of its preconditions
is the wrong mechanical form of a correct intent. The call surface is settled here, once, and plans
01-08, 01-09 and 01-10 conform to it rather than each describing its own dialect.

1. **Part files get their own addressable home, and it is not a `Zone` (HIGH-5).** Cycle 1's memory
   fix told plan 01-08 to flush into `data/_staging/` through `write_table`, but `write_table`
   resolves only through `resolve_table_path`, which requires descendancy of one of the five `Zone`
   directories — and `data/_staging/` is a sibling of all five. Adding a sixth `Zone` member was
   rejected: a zone is a lineage-bearing, DVC-declarable region of the data tree, and staging is
   neither, so widening `Zone` would have made the zone concept mean two different things and would
   have broken the enum-membership criterion this plan already pins. Instead `paths.py` gains a
   parallel resolver, `resolve_staging_path`, with the same absolute-resolve-and-assert-descendancy
   discipline pointed at the staging root, and `repository.py` gains `write_part_file`, which routes
   through `write_parquet_atomic` and records no lineage — not by a flag the caller may forget, but
   because it has no lineage parameter at all. `Zone` keeps exactly its five members and
   `resolve_table_path` keeps exactly its zone-descendancy contract.
2. **The output root is a real parameter on every call that touches disk (HIGH-6).** Four plans
   declared an `out_root` and three CLIs declared `--out`, but no write, read or query function
   accepted a root, so an `out_root` a producer held had nowhere to go — which made plan 01-11's
   two-output-root golden test, and therefore phase success criterion 1, unwritable. `root` is now
   plumbed through the whole surface and forwarded to `resolve_table_path`, `resolve_staging_path`
   and `record_lineage`. Relatedly, `DATA_ROOT` is now defined unambiguously against this module's
   own location rather than against the process working directory: a cwd-derived default would make
   "two output roots" and "two working directories" the same experiment, and plan 01-11 asserts them
   as two distinct properties.
3. **The sort-key precondition is on the tuple, not the last column (HIGH-8).** Requiring the final
   element of `sort_key` to be a unique column is unsatisfiable for `inventory_snapshots`
   `(tick, sku)` and `feature_grid` `(customer_id, as_of_ts)`, where the tuple is unique and the sort
   is a genuine total order but no single trailing column is. Uniqueness of the tuple is exactly the
   property that makes the order total, which is the property byte-identical reruns actually need, so
   that is what is now required and raised on.
4. **A public Arrow type alias so annotations do not breach the import contract (MEDIUM-6).**
   `nextmove.features` must annotate an Arrow return type while plan 01-04's second contract forbids
   it from importing `pyarrow`. `nextmove.storage` therefore re-exports `Table`, and consumers
   annotate against that. The contract is not relaxed and no linter carve-out is added.

**Resolved cross-AI review cycle 3 (HIGH-10, HIGH-13, MEDIUM-7, MEDIUM-10, LOW-6).** Cycle 3 found
that the cycle-2 memory fix *relocated* the materialization instead of removing it: the flush loop
bounded live Python objects, but `write_table_from_parts` then concatenated every part into one Arrow
table and sorted it, so the merge's peak allocation was still the whole table — and both consumer
budget tests measured `tracemalloc` only, which cannot see an Arrow buffer. This is the third
consecutive cycle in which ENG-08 has been asserted ahead of its mechanism. It is closed here by
changing the mechanism rather than the wording, and the change is confined to this plan because this
is where every byte in the project is written.

1. **There is exactly one writer, and it is a stream.** `_parquet.py` gains
   `write_parquet_stream`, which consumes a `pyarrow.RecordBatchReader` and emits fixed-size row
   groups through a `pyarrow.parquet.ParquetWriter`. It never holds more than one row group.
   `write_parquet_atomic` survives as the in-memory convenience — it sorts a table and hands the
   sorted table's reader to the stream writer — so the two paths cannot drift in writer options,
   row-group boundaries or metadata, and the pre-existing byte-equality criteria stay true by
   construction rather than by coincidence.
2. **The merge is out-of-core, not a concatenation.** `write_table_from_parts` now builds a DuckDB
   statement over `read_parquet` of the part paths with an explicit total `ORDER BY` and, when
   `dedupe_on` is given, a `QUALIFY row_number()` reduction, runs it on the existing single-threaded
   connection under an explicit `memory_limit`, and fetches the result as a record-batch stream that
   goes straight into `write_parquet_stream`. DuckDB's sort and window operators spill to disk beyond
   the limit, so the merge's peak is the configured limit plus one row group **at any table size**.
   That is a bound a test can falsify, which the concatenation design was not.
3. **Uniqueness is checked without holding the table.** The sort-key tuple precondition is unchanged
   in meaning but is now enforced on the stream: because the stream is sorted, duplicate tuples are
   necessarily adjacent, so comparing each row's key to the previous row's — carrying one key across
   batch boundaries — detects exactly the same violations in constant memory, with the same message.
4. **A query result can become a part file without passing through Python (HIGH-13).**
   `write_query_to_part` streams a DuckDB result into a staging part file. Plan 01-10's
   `materialize_grid` was specified to feed `query`'s Arrow `Table` into `write_table`'s row-iterable
   parameter — types that do not compose, whose only literal route was a roughly 27.4-million-row
   Python round-trip on the one producer with no memory budget at all. The obvious repair, an
   Arrow-input `write_arrow_table`, was **rejected**: it would make the types compose while leaving
   `query`'s full-grid Arrow materialization exactly where it is, which is precisely the
   move-the-peak-out-of-the-measurement failure this cycle exists to stop. Streaming the query into
   parts removes the materialization instead of relocating it.
5. **Zero parts is a defined case (MEDIUM-7).** A merge over an empty part list has no schema source
   at all, so it raises rather than guessing. Producers that must write a table even when empty call
   `write_table` with an empty row set, which constructs the schema explicitly. That fallback is now
   stated in all three producer plans rather than only in 01-09's rejects branch.
6. **`extra_metadata` and the table-name derivation (MEDIUM-10, LOW-6).** `write_table` and
   `write_table_from_parts` accept optional extra key-value metadata merged into — never over — the
   closed set, which is how plan 01-10 stamps `FEATURE_SET_VERSION`. And the previously unstated
   derivation from `input_paths` to the stamped input *table names* is fixed as the destination
   filename stem.

**Where the memory bound now lives, in one sentence.** Every table in this project is produced by
either an in-memory write whose row count is bounded by a population or catalog count, or a streaming
write whose peak is `STORAGE_MEMORY_LIMIT_MB` plus one row group. No path is bounded by the horizon.

    zone-membership criterion this task pins. A parallel resolver carrying the identical
    absolute-resolve-then-assert-descendancy discipline gives the flush path a real,
    containment-checked destination without touching the zone contract — which is what plan 01-08
    Task 3 and plan 01-09 Task 1 both need in order to bound their peak heap at all.

    Create `src/nextmove/storage/_parquet.py`, the private primitive that owns every byte-level
    determinism control in one place. It must import only `pyarrow`, the standard library, and
    `paths.py`. It must not import the repository module, the lineage module, or the storage package
    root — that restriction is the whole point of the module, and an acceptance criterion greps for
    violations. Declare:

    Declare `PARQUET_ROW_GROUP_SIZE` as a pinned module constant (use `65536`). It is a writer
    option in the same sense as `compression` and `version`: it materially determines the bytes on
    disk, so it is pinned here as a literal rather than exposed as a parameter or a config key. Every
    Parquet file in the project is written in row groups of exactly this size, with only the final
    group short. That single pinned value is what lets a streamed write and an in-memory write of the
    same rows produce identical bytes.

    `write_parquet_stream(batches: pyarrow.RecordBatchReader, dest: Path,
    sort_key: tuple[str, ...], kv_metadata: dict[str, str]) -> Path` — **the single site in this
    project where Parquet bytes are produced.** Open a `pyarrow.parquet.ParquetWriter` on a sibling
    temporary path in the destination directory using the reader's schema and the pinned writer
    options, consume the reader, re-chunk the incoming batches so every emitted row group holds
    exactly `PARQUET_ROW_GROUP_SIZE` rows except the last, close the writer, and `os.replace` onto the
    destination. A reader that yields no rows still produces a file carrying the full schema. Peak
    allocation is one row group plus one incoming batch — never the table — which is the property
    that makes every bound stated elsewhere in this phase achievable rather than aspirational.

    `write_parquet_stream` requires its input stream to already be sorted by `sort_key`, and enforces
    the sort-key **tuple** uniqueness precondition on the stream: hold only the previous row's key
    tuple, compare each row's key against it, and raise `ValueError` naming the sort-key columns and
    the first duplicate tuple value on a match. Because the stream is sorted, duplicate tuples are
    necessarily adjacent, so this detects exactly the violations a whole-table scan would and detects
    them in constant memory. State the sortedness precondition in the docstring — it is the reason
    the check is sound, and a caller feeding an unsorted stream would get a silent false pass rather
    than a loud error.

    Pin the null ordering explicitly to nulls-last on both the sort performed here and every
    `ORDER BY` the repository module generates. PyArrow's `sort_by` and DuckDB's `ORDER BY` both have
    defaults, and two writers disagreeing about where nulls land would produce different bytes for
    the same rows — a determinism defect that would surface only on a table that acquired a nullable
    sort column later.

    `write_parquet_atomic(table: pyarrow.Table, dest: Path, sort_key: tuple[str, ...],
    kv_metadata: dict[str, str]) -> Path` — the in-memory convenience over the stream writer, for
    callers that already hold a whole table and whose row count is bounded by a population or catalog
    count rather than by the horizon. Sort with `Table.sort_by` on the supplied `sort_key` with
    nulls-last placement, then hand the sorted table's reader — chunked at `PARQUET_ROW_GROUP_SIZE` —
    to `write_parquet_stream`. It performs no write of its own. That delegation is the mechanism, not
    a tidiness preference: a second writer would be a second set of row-group boundaries and writer
    options to keep in agreement, and the byte-equality between a merged table and a single-call
    write is asserted by test in Task 3.

    The precondition is on the tuple rather than on its final column, and that distinction is
    load-bearing rather than pedantic. Three of the nine tables this phase writes carry a composite
    key whose trailing column legitimately repeats: `inventory_snapshots` is keyed `(tick, sku)` and
    holds one row per sku per tick, `feature_grid` is keyed `(customer_id, as_of_ts)` and holds one
    row per customer per day, and `ground_truth_uplift` is keyed
    `(customer_id, action_type, tick)`. In every case the tuple is unique and the sort is a genuine
    total order, which is precisely the property byte-identical reruns depend on; a last-column check
    would reject all three while proving nothing extra about the two-column cases. Where a table has
    a single-column key — `catalog` on `sku`, `rejects` on `reject_id` — the tuple check degenerates
    to the column check, so nothing is lost.

    The temporary-path-then-`os.replace` discipline lives in `write_parquet_stream`, so an
    interrupted run leaves no partial table on any path. Attach only the supplied key-value metadata.
    Do not attach any wall-clock value, generation stamp, hostname, or user name: those differ between
    two runs and would break byte-identical comparison at the footer even when every data byte
    matched. Pin the Parquet writer options explicitly (`compression`, `version`,
    `write_statistics`, and `PARQUET_ROW_GROUP_SIZE`) rather than relying on library defaults that
    can shift between releases.

    `read_parquet_file(path: Path) -> pyarrow.Table` — a plain read with no zone logic. It is used
    for small whole-file reads only: the lineage fragment upsert and test fixtures. It is
    deliberately **not** how the part merge reads its inputs — the merge reads through DuckDB so it
    never holds a part, let alone all of them, in memory at once.

    Because every public module routes its writes through `write_parquet_stream`, the lineage
    fragment, every data table, every staging part file and every merged table inherit the identical
    determinism guarantee, and there is exactly one site to audit rather than several that must be
    kept in agreement.

    Create `src/nextmove/storage/repository.py`. Together with `_parquet.py` and `lineage.py` this
    package is the only part of the project permitted to import `pyarrow` or `duckdb` — plan 01-04's
    second import-linter contract enforces that, and the whole `nextmove.storage` package is
    deliberately absent from that contract's source list.

    Declare `Table` as a public module-level alias for `pyarrow.Table`, and re-export it from the
    storage package root. Consumer packages need to annotate the Arrow value they receive back from
    `read_table`, `query` and `compute_as_of`, but plan 01-04's second import contract forbids every
    package except `nextmove.storage` from importing `pyarrow` — so an annotation written directly
    against `pyarrow.Table` would either drive `lint-imports` red or leave an unresolvable name. The
    alias is the sanctioned route: `from nextmove.storage import Table` is an import of this package,
    which every package is permitted, and it keeps exactly one module in the project referring to the
    library by name. The contract is not relaxed and no linter carve-out is added; plan 01-10
    annotates against `Table` for this reason.

    Declare `STORAGE_MEMORY_LIMIT_MB` as a module-level constant (use `512`). It is the ceiling
    DuckDB is told to keep its own working set under; beyond it DuckDB spills its sort, join and
    window state to its temporary directory rather than growing. This constant is deliberately a
    module constant and **not** a config key, by the identical reasoning plan 01-08 applies to
    `flush_every_ticks` and the converse of the reasoning it applies to
    `uplift_snapshot_every_ticks`: the spill threshold changes how much memory a merge uses, never
    which rows come out or in what order, so it must stay outside the hashed config surface or two
    byte-identical runs would carry different config hashes. Task 3 asserts that invariance rather
    than assuming it.

    `connect(read_only: bool = False)` returns a DuckDB connection with `PRAGMA threads=1`,
    `PRAGMA memory_limit='<STORAGE_MEMORY_LIMIT_MB>MB'` and an explicit `PRAGMA temp_directory`
    pointing inside the staging root already applied. Single-threaded execution is not a performance
    choice: DuckDB documents that floating-point aggregates such as standard deviation and
    correlation can differ across runs under parallel execution because the local-then-merge
    summation order is not guaranteed identical, and any table whose bytes are compared in a golden
    test must not carry that variance. The memory limit is likewise not a performance choice: it is
    what converts an out-of-memory *crash* on a large merge into a spill, and — when even the spill
    cannot satisfy a query — into a DuckDB error naming the limit, which is a diagnosable failure
    rather than a machine that swaps to death. Point the temporary directory inside the staging root
    so spill files are covered by the same `.dvcignore` entry and removed by the same
    `clear_staging` call as part files, rather than accumulating somewhere nobody cleans.

    **Every function below that touches disk takes `root: Path | None = None` and forwards it.** A
    producer that accepts an `out_root` — `run_simulation` in plan 01-08, `ingest_events` in plan
    01-09, `compute_as_of` and `materialize_grid` in plan 01-10 — must be able to hand that root to
    the storage layer, or the parameter is decorative. It is not decorative: plan 01-11's headline
    golden test runs the `ci` profile twice into two separate output roots and compares every
    produced file's sha256, and phase success criterion 1 rests on that comparison. `root` is
    forwarded to `resolve_table_path`, to `resolve_staging_path`, and on to `record_lineage`, so a
    run directed at an alternate root writes its lineage fragments there too and nothing leaks back
    into `DATA_ROOT`.

    `write_table(rows, table_name, zone, sort_key, resolved_config, producer_stage: Stage,
    input_paths: Sequence[Path] = (), record_lineage: bool = True,
    extra_metadata: Mapping[str, str] | None = None, root: Path | None = None) -> Path`:
    convert `rows` (an iterable of Pydantic models or mappings) to a `pyarrow.Table` with an
    explicitly constructed schema — never inferred from the first record, because an all-null column
    in a small run would infer a different type than in a large one. Resolve the destination through
    `resolve_table_path` and delegate the sort, the atomic rename and the writer options to
    `write_parquet_atomic`. Stamp key-value metadata with the config hash, the sorted list of input
    *table names*, the `producer_stage`, `CONTRACT_VERSION`, and any `extra_metadata` the caller
    supplied — and nothing else. Deliberately do not stamp input content hashes here: hashes are
    computed once, by the lineage module, from the bytes on disk, and a second computation site would
    be a second thing to keep honest.

    `extra_metadata` is merged into the closed set, never over it: raise `ValueError` naming the
    offending key when a supplied key collides with `config_hash`, `input_tables`, `producer_stage`
    or `contract_version`. The parameter exists because plan 01-10 must stamp `FEATURE_SET_VERSION`
    on `feature_grid` and had no declared route to do so, and because inventing a private route from
    a consumer plan is the drift this plan's single-call-surface rule exists to prevent. Merging
    rather than overriding keeps the four closed keys unforgeable while still letting a producer
    record something only it knows.

    **Derive the stamped input table names from the supplied paths as the destination filename
    stem** — `data/canonical/events.parquet` yields `events`. `write_table` receives
    `input_paths: Sequence[Path]` but must stamp input *table names* and must populate
    `LineageRecordDraft.input_tables: list[str]`, and the derivation between the two was previously
    unstated while `record_lineage`'s parameter tuple is pinned exactly, leaving an executor no way
    to resolve it by adding a parameter. State it here, in one place, and sort the resulting names
    lexicographically before stamping.

    A note on which write path to use, because it is the difference between a bounded producer and an
    unbounded one: `write_table` materializes `rows` as one Arrow table, so it is correct only for
    tables whose row count is bounded by a population, catalog or campaign count. Any table whose row
    count scales with the horizon must be produced by flushing part files and merging them with
    `write_table_from_parts`, or by streaming a query into parts with `write_query_to_part`. Plans
    01-08, 01-09 and 01-10 each state which of their tables falls on which side of that line.

    Raise `ValueError` when `zone` is the lineage zone, naming it. A lineage fragment is produced
    only by `record_lineage`, which writes through the private primitive directly. That refusal is
    the structural reason recording lineage cannot re-enter the write path, and it converts what
    would otherwise be an implicit convention into a checked precondition.

    After a successful write, and only when `record_lineage` is true, call the lineage module's
    `record_lineage`, passing the destination path, the `input_paths`, the `root`, and a hash-free
    draft. Pass no content hash — the lineage module computes every hash itself from disk. The
    `record_lineage` parameter exists so a caller that must persist a table without a lineage row —
    test fixtures building a table to hash-compare — has an explicit, greppable way to say so rather
    than reaching around the repository. It is **not** how staging part files are written; those go
    through `write_part_file` below, which has no lineage parameter to forget.

    `write_table_from_parts(part_paths, table_name, zone, sort_key, resolved_config, producer_stage,
    input_paths=(), record_lineage=True, dedupe_on: str | tuple[str, ...] | None = None,
    extra_metadata: Mapping[str, str] | None = None, root: Path | None = None) -> Path` — merges the
    supplied Parquet part files into one sorted table **out of core**, and never holds more than a
    row group of the result. It carries the same lineage-zone refusal, the same `extra_metadata`
    merge rule and the same input-table-name derivation as `write_table`.

    The merge is a DuckDB statement, not an Arrow concatenation. On the single-threaded connection
    from `connect`, select from `read_parquet` over the list of part paths, with an explicit
    `ORDER BY` naming every element of `sort_key` in order, ascending, nulls last; then fetch the
    result as a `pyarrow.RecordBatchReader` at `PARQUET_ROW_GROUP_SIZE` rows per batch and hand that
    reader directly to `write_parquet_stream`. DuckDB's sort spills to the configured temporary
    directory once it exceeds `STORAGE_MEMORY_LIMIT_MB`, so **the peak allocation of a merge is the
    memory limit plus one row group regardless of how many rows the parts hold.**

    This replaces a design that read every part through `read_parquet_file` and concatenated them
    into one Arrow table before sorting. That design bounded the producer's *Python* heap while
    leaving the merge's Arrow footprint equal to the whole table — which is the entire hazard ENG-08
    names, and which no `tracemalloc`-based test can observe. Record that reasoning in the function's
    docstring, because the next contributor to reach for `pyarrow.concat_tables` here will find it
    simpler and will not otherwise know what it costs. An acceptance criterion greps for exactly that
    call.

    `dedupe_on` names the column or column tuple whose duplicates collapse. Express it in the same
    statement with `QUALIFY row_number() OVER (PARTITION BY <dedupe_on> ORDER BY <sort_key>) = 1`, so
    the surviving row is the first in the global sorted order and the reduction inherits the same
    spill behaviour as the sort. Two properties matter and both are asserted by test. First, the
    surviving row is selected by position in the sorted order rather than by part index, so which
    part a row arrived in cannot change the result. Second, the reduction happens inside the database
    engine, so a producer that needs cross-part deduplication — plan 01-09's `event_id` idempotency
    being the only Phase 1 case — never has to hold its parts, as Python objects or as Arrow buffers,
    to achieve it. Passing `dedupe_on=None` omits the `QUALIFY` clause entirely.

    The merged output is byte-identical to a single `write_table` of the same rows because both
    reach disk through `write_parquet_stream` with the same schema, the same pinned writer options
    and the same pinned row-group size, and because both are sorted on the same total key with the
    same nulls-last placement. That equality is asserted by test in Task 3 and is the reason the
    row-group size is a pinned constant rather than a tunable.

    **An empty `part_paths` raises `ValueError` naming the table**, with a message stating that a
    zero-part merge has no schema source. This is a deliberate refusal rather than an empty file: the
    schema of a merged table comes from its parts, and with no part there is nothing to infer from
    and nothing honest to invent. A producer that must write its table even when no rows were
    produced calls `write_table` with an empty row set instead — `write_table` constructs its schema
    explicitly from the declared model, so it handles zero rows correctly. Plans 01-08, 01-09 and
    01-10 each state that fallback at their own call sites, because plan 01-11 asserts the zero-row
    case end to end and it must be reachable from every producer, not only from 01-09's rejects
    branch.

    `write_query_to_part(sql: str, part_dir: str, part_index: int, sort_key: tuple[str, ...],
    root: Path | None = None, **table_bindings) -> Path` — the streaming counterpart of
    `write_part_file` for producers whose rows come from a query rather than from Python objects. It
    binds each named table from its Parquet path under `root` exactly as `query` does, appends the
    same explicit ascending nulls-last `ORDER BY` over `sort_key` that the merge uses, fetches the
    result as a record-batch stream at `PARQUET_ROW_GROUP_SIZE` rows per batch, resolves its
    destination through `resolve_staging_path`, and hands the stream to `write_parquet_stream`. Like
    `write_part_file` it takes no `zone`, no `resolved_config` and no `record_lineage`, so a part
    file can neither escape the staging root nor acquire a lineage row.

    This function exists because plan 01-10 materializes a feature grid of roughly 27.4 million rows
    at default scale — one row per active customer per day — and the only routes it previously had
    were `query`'s fully materialized Arrow `Table` (which its declared consumer, `write_table`,
    cannot even accept) or a round trip through 27.4 million Python dictionaries. Both hold the whole
    grid. Streaming the query into chunked part files, then merging those parts with
    `write_table_from_parts`, is the same flush-and-merge shape plans 01-08 and 01-09 already use, so
    the phase has one bounded write pattern rather than three unrelated ones.

    Note in the docstring that `root` and every element of `sort_key` are reserved names and cannot
    double as bound table names, for the same reason `query` reserves `root`.

    `write_part_file(rows, part_dir: str, part_index: int, sort_key: tuple[str, ...],
    root: Path | None = None) -> Path` — the staging counterpart of `write_table`, and the only
    sanctioned way to persist a transient part file. It converts `rows` to an Arrow table with an
    explicitly constructed schema exactly as `write_table` does, resolves its destination through
    `resolve_staging_path`, and delegates to `write_parquet_atomic` so a part file inherits the same
    sort, the same atomic rename and the same pinned writer options as every other Parquet file in
    the project.

    It takes no `zone`, so it cannot be pointed at a data zone, and it takes no `record_lineage`
    parameter and never calls the lineage module, so a part file cannot acquire a lineage row by
    accident. That is the design point: a part file is an implementation detail of one run, it is
    deleted before the run exits, and a lineage row describing a file that no longer exists would be
    a provenance claim about nothing. It also carries no `resolved_config` and stamps no key-value
    metadata beyond `CONTRACT_VERSION`, because the merged table is what gets stamped and a part file
    is never itself an artifact.

    `list_part_files(part_dir: str, root: Path | None = None) -> list[Path]` returns every part file
    under that staging directory sorted by filename, which the zero-padded index makes equal to
    numeric order. Sort explicitly rather than trusting `iterdir`: directory order is
    filesystem-dependent, and a merge that consumed parts in filesystem order would make the merged
    bytes machine-dependent — the exact failure this whole layer exists to prevent.

    `clear_staging(part_dir: str | None = None, root: Path | None = None) -> None` removes one
    staging subdirectory, or the whole staging root when `part_dir` is `None`, and is a no-op when
    the target does not exist. It refuses to remove anything that is not a descendant of
    `staging_root(root)`, so a producer cleaning up after itself can never delete a data zone.

    `read_table(table_name, zone, root=None) -> Table`,
    `table_exists(table_name, zone, root=None) -> bool`, and
    `query(sql: str, root: Path | None = None, **table_bindings) -> Table` which opens a

    State plainly in the docstrings of both `read_table` and `query` that they return a **fully
