<objective>
Build the thin repository layer ENG-01 requires and the content-hash lineage DATA-04 requires, and
initialize DVC as the artifact-versioning mechanism ADR 007 ratified (ENG-09 / D-09).

Purpose: this is the single place where determinism is either won or lost. RESEARCH names four
documented nondeterminism sources — unsorted row order, multi-threaded DuckDB float aggregation,
hash-randomized set iteration, and wall-clock metadata in the Parquet footer — and every one of them
is a storage-layer concern. Fixing them once here means every later producer inherits the guarantee
instead of re-earning it.
Output: `write_table` / `read_table` / `query`, a queryable lineage table, a printable lineage chain,
and a golden test proving byte-identical writes before any simulator exists to test with.
</objective>

    `connect(read_only: bool = False)` returns a DuckDB connection with `PRAGMA threads=1` already
    applied. Single-threaded execution is not a performance choice: DuckDB documents that
    floating-point aggregates such as standard deviation and correlation can differ across runs under
    parallel execution because the local-then-merge summation order is not guaranteed identical, and
    any table whose bytes are compared in a golden test must not carry that variance.

    `write_table(rows, table_name, zone, sort_key, resolved_config, input_tables=()) -> Path`:
    convert `rows` (an iterable of Pydantic models or mappings) to a `pyarrow.Table` with an
    explicitly constructed schema — never inferred from the first record, because an all-null column
    in a small run would infer a different type than in a large one. Sort with `Table.sort_by` on the
    supplied `sort_key` tuple immediately before writing; require the final element of `sort_key` to
    be a column with unique values and raise if it is not, so the order is provably total. Write to a
    sibling temporary path in the same directory and `os.replace` onto the destination once the write
    completes, so an interrupted run leaves no partial table. Stamp Parquet key-value metadata with
    the config hash, the sorted input-hash list, and `CONTRACT_VERSION` — and nothing else. Do not
    stamp any wall-clock value, generation timestamp, hostname, or user name: those differ between
    two runs and would break byte-identical comparison at the footer even when every data byte
    matched. Pin the Parquet writer options explicitly (`compression`, `version`, `write_statistics`)
    rather than relying on library defaults that can shift between releases. After the rename,
    call `record_lineage` from the lineage module with the hash of the bytes actually on disk.

    `read_table(table_name, zone) -> pyarrow.Table`, `table_exists(table_name, zone) -> bool`, and
    `query(sql: str, **table_bindings) -> pyarrow.Table` which opens a single-threaded connection,
    registers each bound table by name from its Parquet path, executes the SQL, and returns an Arrow
    table. `query` is how `features/` reaches DuckDB without importing it.

    Re-export the public names from `src/nextmove/storage/__init__.py`.

  <action>
    Create `src/nextmove/storage/lineage.py`.

    `content_hash(path: Path) -> str` reads the file in chunks and returns the sha256 hex digest of
    its exact bytes. This function is the only source of a content hash: `record_lineage` must never
    accept a hash as a caller-supplied argument for the table being described. A producer that could
    assert its own hash could assert a false one, and DATA-04's whole value is that the lineage is
    checkable rather than claimed.

    `LineageRecord` is a Pydantic model with fields `table_name: str`, `zone: str`,
    `content_hash: str`, `input_hashes: list[str]`, `input_tables: list[str]`, `config_hash: str`,
    `contract_version: str`, `producer_stage: str`, and `row_count: int`. Deliberately no timestamp
    field of any kind — a wall-clock column would make the lineage table itself differ between two
    otherwise-identical runs, which is the exact failure the storage layer exists to prevent.
    Ordering within the lineage table is by `table_name`, which is unique.

    `record_lineage(record: LineageRecord, root: Path | None = None) -> None` reads the existing
    lineage Parquet table from the `canonical` zone if present, replaces any row with the same
    `table_name`, sorts `input_hashes` and `input_tables` lexicographically before storing, sorts the
    whole table by `table_name`, and writes it back through the repository's sorted atomic write.

    `read_lineage(root=None) -> list[LineageRecord]` and
    `print_lineage_chain(table_name: str, root=None) -> str` — the latter resolves the named table's
    row, walks `input_tables` transitively depth-first with children visited in sorted order, and
    returns an indented text rendering showing each table's name, short content hash, config hash and
    row count. A table with no inputs renders as a root node line; a cycle raises with the cycle
    named rather than recursing forever. Return the string and also print it, so a `just` recipe and
    a test can both use it.

    Initialize DVC: run `dvc init --no-scm-checks` if needed so `.dvc/` and `.dvcignore` exist,
    configure `core.autostage = true` and `core.analytics = false` in `.dvc/config` (no telemetry, no
    cloud dependency per ENG-08), and add `.dvcignore` entries for `.venv/`, `__pycache__/` and
    `tests/`. Do not configure a remote — ENG-08 forbids a cloud dependency and DVC's local cache is
    sufficient for the laptop-only guarantee. Do not create `dvc.yaml` here; plan 01-11 owns the
    pipeline stages once all three producers exist.
  </action>
